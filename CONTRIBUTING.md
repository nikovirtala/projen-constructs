# Contributing

Thanks for your interest in improving `@nikovirtala/projen-constructs`. This guide covers how the repository is built, how to set it up locally, and how to propose changes.

## This project generates itself with projen

The repository is managed by [projen](https://projen.io). `.projenrc.ts` is the single source of truth: it defines the project using the `JsiiProject` type from this very library, and running projen regenerates the rest of the configuration (`package.json`, `tsconfig*.json`, `vitest.config.ts`, `biome.jsonc`, `mise.toml`, the GitHub workflows, and more).

Because of this, there is one rule that matters more than any other:

> **Never hand-edit generated files.** Change `.projenrc.ts` (or the helpers in `src/` it uses) and run `pnpm projen` to regenerate.

Generated and linguist-generated files carry a `~~ Generated by projen` header or are listed in `.projen/files.json`. This also includes `src/project-type.ts` and everything under `src/projects/*.generated.ts`, which are produced by the `ProjectGenerator` component during synthesis. Editing any of these by hand is pointless: the next synth overwrites your change.

Files you *can* edit directly include `.projenrc.ts`, the non-generated sources under `src/` (`src/components/*.ts`, `src/config.ts`, `src/errors.ts`, `src/utils.ts`, `src/versions.json`), the tests under `test/`, and the hand-written docs (`README.md`, `docs/*.md`, `.kiro/steering/*.md`, and the root markdown files like this one).

## Local setup

- **Node.js** `>= 26.13.0`. The version is managed with [mise](https://mise.jdx.dev) via `mise.toml`; run `mise install` to get the pinned toolchain.
- **pnpm 12** is the package manager (pinned to `12.16.1`). `corepack enable` will resolve it automatically from `package.json`.

Install dependencies:

```bash
pnpm install
```

## Key commands

| Command | What it does |
| --- | --- |
| `pnpm projen` | Regenerate all projen-managed files from `.projenrc.ts`. Run this after any config change. |
| `pnpm build` | Full build: synth, compile with JSII, run tests, and generate docs. |
| `pnpm test` | Run the Vitest unit tests (with tsc type checking). |
| `pnpm biome` | Format and lint with Biome. |
| `pnpm docgen` | Regenerate `API.md` with jsii-docgen. |
| `pnpm update-versions` | Refresh `src/versions.json` with the latest AWS CDK, Node.js, and TypeScript versions. |

## Running tests

Unit tests live in `test/**` and run with [Vitest](https://vitest.dev):

```bash
pnpm test
```

Integration tests under `test/integration/` build and pack the package into a temporary directory and exercise the generated projects. They are heavier and environment-sensitive, so run the unit suite for day-to-day work and rely on CI for the full matrix.

## Commits, PR titles, and releases

- Follow [Conventional Commits](https://www.conventionalcommits.org). The commit type drives the changelog and the next version number.
- **Pull request titles are linted** by the `pull-request-lint` workflow and must also follow Conventional Commits. Use `feat!:` / `fix!:` (or a `BREAKING CHANGE:` footer) for breaking changes.
- Releases are automated with [commit-and-tag-version](https://github.com/absolute-version/commit-and-tag-version) from the merged commit history. You do not bump versions or edit `CHANGELOG.md` by hand for a release.

## Proposing a change

1. Fork the repository and create a feature branch off `main`.
2. Make your change in `.projenrc.ts` and/or the editable sources, then run `pnpm projen` so the generated files are in sync.
3. Run `pnpm build` (or at least `pnpm test` and `pnpm biome`) and commit every file the workflow touched, including regenerated output.
4. Open a pull request with a Conventional Commit style title and a clear description of the change.
